# macOS・Windows・WSLgでEmacsキーバインドを統一する日本語入力環境

## Q1. 何を実現したいのか？

macOS、Windows、Linux（特にWSLg）のいずれでも、Emacsベースのキーバインドを使って日本語を入力・編集できる環境を実現したい。

目的は、単に日本語入力ができることでも、同じIMEをすべてのOSで動かすことでもない。

重要なのは、OSやアプリケーションの違いを意識せず、同じキー操作で以下を行えることである。

- Emacs風のカーソル移動や文字削除
- 日本語の読みの入力と編集
- 漢字変換候補の選択
- 一括変換後の文節間移動
- 文節の範囲の伸縮
- 変換の確定や取り消し

特に、一括変換後に文節の区切りを修正できることは必須である。

IMEそのものを自作することも許容するが、既存の変換エンジンを利用して目的を実現できるなら、その方が望ましい。

## Q2. 必要なのは共通IMEなのか、それともIMEのラッパーなのか？

必要なのは、日本語変換エンジンの共通化よりも、入力操作の共通化である。

日本語入力環境は、大きく次の要素に分けられる。

```
キーボード
    |
    v
キー入力の解釈
    |
    v
入力状態に応じた操作の決定
    |
    v
日本語変換エンジン
    |
    v
OS・アプリケーションのテキスト入力機構
```

このうち、統一したいのは主に「キー入力の解釈」と「入力状態に応じた操作」である。

したがって、必ずしも実行時にキーイベントを横取りするラッパーを開発する必要はない。

既存IMEの設定機構を利用して共通の操作体系を実現し、その設定の生成・配布・適用を管理する方法もある。

今回の第一候補は後者である。

## Q3. なぜEmacsキーバインドの統一には、単純なキーリマッパーでは不足するのか？

同じキーが入力状態によって異なる意味を持つためである。

例えば `C-f`（Ctrl+F）は、通常のテキスト編集中なら1文字進む操作として扱いたい。一方、日本語変換中なら次の文節へ移動する操作として扱いたい。

| キー    | 読みの入力中     | 漢字変換中   |
| ----- | ---------- | ------- |
| `C-f` | 1文字進む      | 次の文節    |
| `C-b` | 1文字戻る      | 前の文節    |
| `C-a` | 読みの先頭へ     | 最初の文節   |
| `C-e` | 読みの末尾へ     | 最後の文節   |
| `C-n` | 候補表示中なら次候補 | 次候補     |
| `C-p` | 候補表示中なら前候補 | 前候補     |
| `C-h` | 前の文字を削除    | 別途定義    |
| `C-g` | 入力を取り消す    | 変換を取り消す |

これは目標とする操作体系の例であり、具体的な割り当ては調整可能である。

Karabiner-ElementsやAutoHotkeyなどのキーリマッパーは、キーイベントの置き換えには適している。しかし、IMEが現在どの状態にあるかを認識し、その状態に応じて変換操作を切り替える用途には向いていない。

したがって、IME内部の状態に応じたキーマップを利用する方が自然である。

## Q4. 文節の範囲を調整するとは、具体的にどのような操作か？

一括変換された日本語の文節境界を変更する操作である。

例えば、次の読みを入力する。

```
ここではきものをぬぐ
```

この文章には、文節の区切り方によって異なる解釈がある。

```
ここで / 履物を / 脱ぐ
```

```
ここでは / 着物を / 脱ぐ
```

変換結果が意図したものと違う場合、変換を最初からやり直すのではなく、対象の文節を選んで境界を伸縮したい。

必要な操作は主に次の4種類である。

- 前後の文節への移動
- 現在の文節を短くする
- 現在の文節を長くする
- 現在の文節の変換候補を変更する

文節境界の変更に応じて変換候補を再計算する必要があるため、文字列の単純な編集とは異なる。

これは日本語変換エンジンと連携して処理すべき操作である。

## Q5. 既存IMEで、この要求を満たせるものはあるか？

第一候補はMozcである。

Mozc は、Google日本語入力を起源とするオープンソースの日本語入力システムであり、状態ごとのキーバインドをカスタマイズできる。

Mozcには、次のような入力状態がある。

| 状態               | 意味        |
| ---------------- | --------- |
| `Direct`         | IMEオフ     |
| `Precomposition` | IMEオン・未入力 |
| `Composition`    | 読みを入力中    |
| `Conversion`     | 漢字変換中     |
| `Suggestion`     | 入力候補の提示中  |
| `Prediction`     | 予測変換中     |

さらに、文節操作のためのコマンドも用意されている。

| Mozcコマンド             | 操作      |
| -------------------- | ------- |
| `SegmentFocusLeft`   | 前の文節へ移動 |
| `SegmentFocusRight`  | 次の文節へ移動 |
| `SegmentWidthShrink` | 文節を短くする |
| `SegmentWidthExpand` | 文節を長くする |
| `ConvertNext`        | 次の変換候補  |
| `ConvertPrev`        | 前の変換候補  |
| `Commit`             | 変換を確定   |
| `Cancel`             | 変換を取り消す |

このため、独自の日本語変換エンジンを作らなくても、今回必要な操作の多くを実現できる見込みがある。

ただし、OSやMozcのバージョンによって利用できる機能やキーイベントの扱いに差がある可能性は残る。

## Q6. Emacs風キーバインドをMozcにどのように割り当てるか？

基本方針は、Emacsの操作概念を維持しつつ、変換中だけ日本語入力固有の意味を与えることである。

例えば、変換中の割り当てを次のようにする。

| キー    | 操作    |
| ----- | ----- |
| `C-b` | 前の文節  |
| `C-f` | 次の文節  |
| `C-p` | 前の候補  |
| `C-n` | 次の候補  |
| `C-g` | キャンセル |
| `C-m` | 確定    |

文節の伸縮はEmacsの標準操作に直接対応するものがないため、別途キーを割り当てる。

候補としては `C-S-b` と `C-S-f` などがある。

複数ストロークを利用することも考えられるが、Mozcの標準キーマップで扱える操作には制約があるため、当初は単一キーイベントの組み合わせを優先する。

また、`C-i` とTab、`C-m` とEnterのように、入力経路によって区別できない可能性のあるキーにも注意する。

## Q7. IMEがオンのとき、Emacsのキー操作を常にIMEが受け取るべきか？

そうではない。

IMEがオンであっても、読みを入力していない状態では、原則としてアプリケーション側のキーバインドを利用したい。

例えば、通常のテキストエリアで `C-n` を押した場合は、Emacs風の次行移動として扱いたい。

一方、漢字変換中なら、同じ `C-n` を次の変換候補へ移動する操作として扱いたい。

この区別を整理すると、次のようになる。

| 状態        | キー操作の担当    |
| --------- | ---------- |
| IMEオフ     | アプリケーション   |
| IMEオン・未入力 | 原則アプリケーション |
| 読み入力中     | IME        |
| 漢字変換中     | IME        |

つまり、EmacsキーバインドをIME内部だけで完結させるのではなく、通常のテキスト編集と日本語変換を連続した操作体系として扱う必要がある。

## Q8. macOS・Windows・Linuxで同じMozcの設定を利用できるか？

共通化できる部分は多いが、すべての環境で完全に同じ動作になるとは限らない。

構成としては、以下が候補になる。

| 環境           | 日本語入力              |
| ------------ | ------------------ |
| macOS        | Mozc系の入力メソッド       |
| Windows      | Google日本語入力またはMozc |
| Linux / WSLg | Fcitx5 + Mozc      |

共通のキーマップを利用すれば、IME内部の操作はかなり統一できると考えられる。

ただし、実際のキー入力にはOSやアプリケーションのショートカット処理も関与する。

例えば、Mozcに `C-n` の操作を定義しても、そこに到達する前に別のコンポーネントがキーを消費する可能性がある。

したがって、キーマップの一致と実際の操作の一致は区別する必要がある。

## Q9. WSLgでは何が問題になるか？

WSLgでは、Windows側とLinux側で入力メソッドの処理が分かれる。

概念的には次のような構成になる。

```
Windows
  |
  +-- Windowsアプリ
  |      |
  |      +-- Windows側IME
  |
  +-- WSLg
         |
         +-- Linux GUIアプリ
                |
                +-- Fcitx5
                       |
                       +-- Mozc
```

Windows側でIMEを設定しただけでは、Linux GUIアプリに同じ設定が適用されるとは限らない。

さらに、WindowsからWSLgへのキーイベント転送、Wayland/XWayland、Fcitx5などが関係する。

したがって、WSLgでは特に以下を確認する必要がある。

- キーイベントがLinuxアプリまで届くか
- Fcitx5が必要なキーを受け取れるか
- Mozcの文節操作が動作するか
- Windows側のショートカットと競合しないか

WSLgを単なるLinux環境として扱わず、WindowsとLinuxの境界を含めて設定・検証する必要がある。

## Q10. Firefoxのようなアプリケーションで `C-n` が奪われる問題はどうするか？

Firefoxでは、Windows・Linuxにおける `Ctrl+N` が通常「新しいウィンドウを開く」に割り当てられている。

今回の要求では、通常のテキストエリアで `C-n` を押した際、このブラウザーのショートカットが発動しないようにしたい。

重要なのは、Firefox自身に次行移動を実装させることではない。

Firefoxのショートカットを無効化できれば、その後のEmacs風キー操作は別の仕組みで実現できる。

Firefox 147以降には、ショートカットを変更するための `about:keyboard` が導入されている。

設定手順は次のとおりである。

1. Firefoxで `about:keyboard` を開く。
2. `New Window` を探す。
3. `Ctrl+N` の割り当てを削除する。
4. テキストエリアで `Ctrl+N` を押し、新しいウィンドウが開かないことを確認する。

この機能を利用できれば、Firefoxを独自ビルドする必要はない。

ただし、ショートカットのカスタマイズ機能は実験的な扱いであるため、利用するFirefoxのバージョンや環境で動作確認する。

## Q11. Firefoxのショートカットを解除した後、通常のテキスト編集はどう実現するか？

Firefoxのショートカット解除と、Emacs風のテキスト編集操作の実装は別の問題である。

今回の構成では、責務を次のように分ける。

```
Ctrl+N
   |
   +-- 日本語変換中
   |      |
   |      +-- Mozc: 次の候補
   |
   +-- 通常のテキスト編集中
          |
          +-- OS・アプリ側の
              Emacs風キーバインド
```

Linuxの場合、GTK側のEmacs風キーバインド設定が利用できる場合がある。

macOSやWindowsについては、それぞれのテキスト入力機構やキーリマッパーなどを利用して、通常の編集操作を補うことになる。

ただし、すべてのアプリケーションが同一の編集機構を利用するわけではない。

今回の方針では、この部分を完全に単一の仕組みで実現する必要はない。アプリケーション側のショートカットが競合せず、必要なキーイベントを扱える状態にすることを優先する。
